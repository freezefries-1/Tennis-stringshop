Architecture and data model

01 · Stack review

Your proposed stack is sound. Next.js + TypeScript + Tailwind + Supabase Postgres is the right weight for this: one person, one shop, a few thousand rows a year, accessed from a bench computer and a phone. It gives you a managed database with automatic backups, a hosted URL you can open on the iPhone, and a codebase Claude can keep working in. I would keep it, with three changes.

Keep
  • Next.js App Router on Vercel — server components and server actions mean no separate API layer to maintain.
  • Supabase Postgres — you need real relational integrity and point-in-time backups. SQLite on a single box would be simpler but backup and phone access get worse, not better.
  • Tailwind, with the SportCraft tokens mapped into tailwind.config so the design system is the palette.
Change
  • Drop the ORM abstraction debate — use Drizzle. Typed SQL, migrations in the repo, no hidden query behaviour. Prisma's client generation step is friction you do not need.
  • Skip Supabase Auth, but do not skip the front door. See the flag below.
  • No state library, no React Query at first. Server components fetch; server actions mutate; revalidatePath refreshes. Add client caching only where the POS proves it needs it.
Must fix"No authentication" cannot mean "no lock".

A public Vercel URL holding customer phone numbers and your P&L is a real risk, and Singapore's PDPA applies to customer contact data regardless of business size. You do not need accounts, roles, or a login system — you need one gate. Cheapest option that satisfies the brief: Vercel Deployment Protection (password on the whole deployment, zero code). Next cheapest: a single shared passcode checked in middleware, stored as an env var, set in an httpOnly cookie for 90 days. Either is about an hour of work and neither adds a users table.

02 · Contradictions, gaps and traps

IssueWhat the brief says, and what I propose
Tension unitsSection 6 shows 50 lbs, the design system shows 24 / 23 kg. Store tension as numeric plus a unit enum per job, canonicalise to kg in a generated column for analytics, and set a display default in Settings. Never convert on write.
Strings are two thingsStrings appear under both Products (section 11: "string reels", "string sets") and String Inventory (section 8). Two tables would desync. One products table with stock_mode = 'unit' | 'length'; length-mode products carry gauge, colour, material and reel length and are the only ones consumable by a string job.
Racket IDsYour example numbers rackets R001–R003 per customer. Per-customer numbering breaks as soon as you merge duplicate customers. Use a global sequence (R-0417) and show a per-customer position in the UI if you want it.
Inventory as expenseFlagged in your own section 16, and it is the single easiest way to wreck the numbers. Resolution below in §05 — stock purchases are never operating expenses.
DiscountsDiscount exists on the string job (section 6) and on the POS sale (section 12). If both apply you can discount twice. Discount lives on the sale only; the job carries list charges.
Customer stringWhen string_supplied_by_customer is true there is no inventory deduction and no string COGS — only labour revenue. Needs to be enforced in the mutation, not left to the operator.
Hybrid usageA hybrid using the same reel for mains and crosses must deduct twice from one batch, not fail a uniqueness assumption. Model usage as n rows, not two fixed columns.
Sets vs metresA string set sold over the counter is a unit sale. A set used in a job is 1 unit, not 11 m. Both paths must exist; only reels use metres.
Job price vs sale priceSection 6 gives the job a "final price"; section 13 says the POS must not duplicate it. Treat job pricing as a quote; the sale is the only money record.
"Last visit"Derived, never stored — it is max() of sale and job dates. Same for lifetime spend, job count, average tension. A stored copy will drift.
Racket catalogueSection 5's Brand → Series → Model → Generation is four levels, but head size and pattern only exist at generation level. Model the first three as lookup rows and put specs on racket_models (the generation row). Archive, never delete — customer rackets point at it.
ReturnsSection 26 asks for correct handling but no mechanism is specified. Never edit or delete a sale: post a reversing sale with negative quantities linked by reverses_sale_id. Inventory movements reverse with it.
Need your callThree decisions I cannot make for you.
  1. GST. If SportCraft is GST-registered, tax has to be in the schema from day one — retrofitting it into historical sales is painful. Say so now and I will add tax_rate and tax_amount snapshots to sale items.
  2. Deposits. Do you ever take payment before a job is collected? If yes, the sale and the collection are separate events and payment status needs a partial state.
  3. Historic Sheets data. Do your existing rows have real costs per reel, or only selling prices? If cost history is missing, imported jobs get a null COGS and reports need to say so rather than quietly showing 100% margin.

The snapshot rule. Every column marked snapshot is written once at transaction time and never recomputed: sale_items.description, sale_items.unit_price_cents, sale_items.cogs_cents, inventory_movements.unit_cost_cents, string_jobs.racket_label. Editing a product's price, a customer's name or a racket's specs afterwards changes nothing historical. Reports read snapshots, never joins to current catalogue prices.

  • A customer has many rackets, jobs and sales. A sale may have no customer (walk-in).
  • A customer racket has many string jobs — that is its service history. It points at a catalogue racket model for specs, so two identical frames are two rows pointing at the same model.
  • A string job has one or two string_job_strings rows, each naming the product, the batch it came from and the metres used.
  • A string job has at most one sale item (UNIQUE(string_job_id)). That constraint is what makes double-billing impossible at the database level, not just in the UI.
  • Every stock change is an inventory movement row against a batch. Quantity on hand is sum(qty_delta), not a stored field.

05 · String jobs, sales, COGS and inventory — one revenue ledger

The rule

A string job is a work order. It is not money. Revenue exists only in sale_items.

Every report that says "revenue" sums sale_items.line_total_cents. Every report that says "COGS" sums sale_items.cogs_cents. Nothing else is ever added. A job with no sale item is unbilled work, and the dashboard should show that number — it is the most useful error report you will have.

The flow

  1. Job created. Strings and tensions recorded. Quoted price computed from labour + string charge + services, but nothing is posted.
  2. Job marked completed. Now string is physically used, so inventory moves: one inventory_movements row per string_job_strings row, movement_type = 'string_job', ref_id = job.id, negative metres, consuming the oldest open batch. Each row snapshots that batch's unit_cost_cents. Their sum is the job's string COGS. Still no revenue.
  3. Job charged at the POS. The job appears in the POS as a pending line. Adding it creates one sale_item with line_type = 'string_job', string_job_id set, cogs_cents = the sum from step 2. Other items (overgrips, a reel, a paddle) are ordinary product lines on the same sale, each consuming their own batches and snapshotting their own cost.
  4. Sale completed. Payment method recorded. Marking the job collected is a separate status change that posts nothing.

Why this cannot double-count

  • The unique constraint on sale_items.string_job_id means a job can be charged exactly once, ever. A second attempt is a database error, not a duplicate row.
  • Job prices are never summed by any report. If you change a job's labour charge after it is billed, the sale is untouched — which is correct, and visible as a variance if you want to report on it.
  • Inventory moves at completion, revenue posts at sale. They are separately traceable, so a job that used string but was never charged shows up in both the "unbilled jobs" list and a gross-margin check.

And the inventory-vs-expense trap

Buying stock is not an expense — it converts cash into inventory. It becomes COGS only when the item is sold. So: stock purchases are entered through Receive stock, which writes an inventory_batch. They are never entered in Expenses. The Expenses section keeps its "Inventory" category for things like packaging or a bulk consumable you do not track as stock, and that category is flagged is_inventory = true so it is excluded from operating expenses in the P&L. If you record a reel purchase in both places, net profit is understated by the cost of the reel, twice.

06 · Buying the same string at different prices

Use batch-level FIFO. Every receipt of stock creates an inventory_batches row with its own unit_cost_cents and its own remaining quantity. Consumption walks the oldest open batch first and records which batch it took from.

Hyper-G 1.25 green
  B-07  12 Mar  200 m @ $180  →  $0.90 / m   qty_remaining 0.0
  B-11  02 Jun  200 m @ $196  →  $0.98 / m   qty_remaining 137.5

  SC-1042  11.0 m  from B-07  →  COGS $9.90   stays $9.90 forever
  SC-1118  11.0 m  from B-11  →  COGS $10.78
  SC-1119  11.0 m  spanning   →  4.0 m B-07 @0.90 + 7.0 m B-11 @0.98 = $10.46

Why FIFO and not weighted average

  • It matches the physical reality. You finish the reel on the machine before opening the next one. FIFO is what actually happens at the bench; weighted average is a fiction you would have to maintain.
  • Per-job cost stays explainable. "This job cost $9.90 because it came off the March reel" is auditable a year later. A moving average cannot be reconstructed without replaying every purchase.
  • Nothing rewrites history. A weighted-average system recalculates the average on every purchase, which is exactly the "changing cost corrupts old profits" failure your brief calls out.
  • The complexity is small. One extra table and a consume-from-batches function. Reporting "inventory value" becomes sum(qty_remaining × unit_cost_cents), which is also more accurate than an averaged figure.

Two details. Spanning batches: when a job needs more than the oldest batch holds, split it into two movement rows — the schema already allows that since movements are per batch. Reel offcuts: a reel that runs out at 4 m remaining leaves a stub; add a write_off movement so inventory value does not carry unusable string. One click from the stock screen.
